Переменные окружения:
env, export, PATH, разница между .bashrc, .bash_profile, .profile.

Тема важная — переменные окружения объясняют, почему одна и та же команда может "работать в одном терминале и не работать в другом",
и почему после установки программы иногда нужно перезапускать терминал.

Что такое переменная окружения вообще

Это просто именованное значение, которое хранится в памяти shell-сессии и доступно программам, которые ты запускаешь из этого терминала.
Проще говоря — "настройки", которые видит вся система, а не только один конкретный скрипт.

Посмотреть все текущие переменные окружения:
	
	env

Выведет длинный список вида ИМЯ=значение, например:

	HOME=/home/burmalda
	SHELL=/bin/bash
	PATH=/usr/local/bin:/usr/bin:/bin
	USER=burmalda
	LANG=ru_RU.UTF-8

Посмотреть одну конкретную переменную:
	
	echo $HOME
	echo $USER
	echo $PATH

Обрати внимание на $ — без него bash воспримет HOME как обычное слово, а не как переменную, которую нужно подставить.

Локальные переменные vs переменные окружения

Это первый момент, где новички путаются. Есть два разных уровня:

Локальная (shell) переменная — видна только внутри текущей сессии shell, дочерние процессы её не видят:
	
	MY_VAR="hello"
	echo $MY_VAR        # покажет "hello"
	bash                 # запускаем дочерний shell
	echo $MY_VAR         # тут будет ПУСТО — переменная не передалась
	exit                  # выходим обратно

Переменная окружения (exported) — видна не только текущему shell, но и всем процессам/скриптам, которые из него запускаются:
	
	export MY_VAR="hello"
	bash                         # дочерний shell
	echo $MY_VAR                  # теперь покажет "hello" — унаследовалась!
	exit

export превращает обычную переменную в переменную окружения — то есть "передаёт её по наследству" всем дочерним процессам.

	export API_KEY="secret123"

Практический смысл: 
если ты пишешь скрипт на Python или Node.js и ему нужен доступ к какому-то значению (например, токену API), ты не хардкодишь его в коде — а делаешь export, 
и программа читает его из окружения:

	import os
	key = os.environ.get("API_KEY")

Это стандартная практика в DevOps — секреты, конфигурация окружения (dev/staging/prod) передаются именно через переменные окружения, а не зашиваются в код.
Отсюда, кстати, растут ноги у .env файлов, которые ты наверняка видел в проектах.

Важный нюанс: export, сделанный руками в терминале, живёт только пока открыта эта сессия терминала. Закрыл терминал — переменная исчезла. 
Чтобы она сохранялась постоянно, её нужно прописать в файле конфигурации shell (о них — ниже).


1. PATH — самая важная переменная окружения

PATH — это список директорий, где shell ищет исполняемые файлы команд, когда ты что-то запускаешь.

	echo $PATH	#/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin:/snap/bin

Пути разделены двоеточием :. Когда ты пишешь ls в терминале, происходит вот что: shell не знает магически, что такое ls — он идёт по каждой папке из PATH слева направо 
и ищет там файл с именем ls. Как только находит — выполняет именно его.

Проверить, откуда конкретно берётся команда:
	
	which ls	#/usr/bin/ls

Почему это важно на практике: если ты установил программу, а терминал пишет command not found — почти всегда причина в том, что программа установилась в папку, которой нет в PATH. 
Решение — либо переместить, либо (правильнее) добавить путь в PATH:

	export PATH="$PATH:/opt/my_program/bin"

Обрати внимание на паттерн $PATH:/новый/путь — ты не заменяешь весь PATH, а дописываешь к уже существующему списку.
Если написать просто export PATH="/opt/my_program/bin" — сотрёшь весь путь, и даже ls перестанет работать до перезапуска терминала.



2. Файлы конфигурации shell — вот где вся путаница

Это те файлы, куда прописывают export и прочие настройки навсегда, чтобы они подхватывались при каждом новом терминале. Разница между ними — в том, когда именно они выполняются.

Чтобы понять разницу, нужно различать два типа shell-сессий:

Login shell — сессия, которая начинается с полноценного входа в систему (SSH-подключение, вход через консольный логин без графики). 
Bash в этом случае считает, что "пользователь только что вошёл в систему".

Non-login (interactive) shell — обычное открытие терминала в уже работающей графической системе 
(например, ты открываешь новое окно терминала на своём десктопе поверх уже залогиненной сессии).


Файл			Когда выполняется								Для чего использовать
~/.bash_profile		Только при login shell								Разовая настройка при входе — например, автозапуск чего-либо один раз за сессию
~/.profile		Login shell, если нет .bash_profile (более универсальный, не только для bash)	То же самое, но кросс-shell вариант (работает и с sh, и с другими shell)
~/.bashrc		Каждый новый interactive shell (в том числе каждое новое окно терминала)	Алиасы, функции, PATH, всё, что должно быть доступно в любом терминале


Практическое правило, которое реально стоит запомнить: в 95% случаев на десктопе (Ubuntu/Debian и подобные) тебе нужен именно ~/.bashrc — потому что каждое открытие нового окна терминала —
это новый interactive non-login shell, и именно .bashrc подхватывается в этот момент.

.bash_profile/.profile реальны и важны в основном при SSH-подключении к серверу — там ты действительно логинишься заново каждый раз.

Кстати, часто на практике .bash_profile просто содержит строчку, которая подгружает .bashrc:

	# в .bash_profile
	if [ -f ~/.bashrc ]; then
	  source ~/.bashrc
	fi
Это сделано, чтобы не дублировать настройки в двух местах — независимо от того, login это shell или нет, всё равно подхватится .bashrc.

Как прописать переменную "навсегда"

	nano ~/.bashrc

В конец файла добавляешь:

	export MY_VAR="hello"
	export PATH="$PATH:/opt/my_program/bin"

Сохраняешь, но простое сохранение файла не применит изменения в уже открытом терминале — нужно либо перезапустить терминал, либо выполнить:

	source ~/.bashrc

source (короткий алиас — точка .) заставляет shell перечитать файл и применить изменения в текущей сессии немедленно, без перезапуска.
